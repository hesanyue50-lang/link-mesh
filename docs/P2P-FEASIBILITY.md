# P2P 跨网可行性评估（零成本约束）

> 结论先行：**双层 NAT / 对称型双层 NAT 下，任何"纯打洞"方案都不可能稳定成功**，这是 NAT 机制决定的，不是实现问题。零成本下可用的组合是「IPv6 直连 + 双层 UPnP/NAT-PMP + 主机中转兜底」，不要指望单靠 STUN 打洞。

## 一、当前实测状态

- 设备：Wi-Fi（192.168.0.x）→ 路由器（192.168.1.x）→ 光猫拨号，**双层 NAT**
- UPnP 成功映射到第二层（`192.168.1.27:45900`），但外部 IP 是私有地址 → 只穿透了一层
- STUN 能拿到 srflx，但对端同样在双层 NAT 后，双方 srflx 都不可直连
- 结论：这不是代码 bug，是网络拓扑问题

## 二、零成本方案对比

| # | 方案 | 成本 | 成功率 | 实现难度 | 主要限制 |
|---|---|---|---|---|---|
| 1 | **IPv6 直连**（已实现候选） | 0 | 中高 | 低（已做） | 双方都要有公网 IPv6；多数家庭宽带已支持，移动网络常为 IPv6-only |
| 2 | **双层 UPnP / NAT-PMP** | 0 | 中 | 低（已做单层） | 需要两级设备都支持且允许映射；运营商 CGNAT 无法映射 |
| 3 | **公共 STUN + ICE**（已实现） | 0 | 低（对称 NAT） | 低 | 对称型 NAT 下必然失败 |
| 4 | **虚拟局域网**（ZeroTier / Tailscale） | 0（免费额度） | **高** | 中 | 依赖第三方根服务器；需要账号/客户端，违反"无账号"的产品原则 |
| 5 | **自建 TURN**（用户自有公网服务器） | 0（已有服务器时） | **高** | 中 | 必须有公网服务器；流量成本由服务器承担 |
| 6 | **免费公共 TURN** | 0 | — | — | 不存在可靠的长期免费 TURN |
| 7 | **第三方 WebSocket 中继**（Cloudflare Workers 等） | 0（免费额度） | 高 | 中 | 依赖第三方、延迟高、有配额 |
| 8 | **浏览器主机中转**（阶段三已实现） | 0 | **100%** | 已完成 | 要求两端都能访问同一台主机；不是真正的 P2P |
| 9 | **反向隧道**（frp / ngrok 免费版） | 0 | 中 | 中 | 需要一台常开设备做跳板，免费版有带宽/时长限制 |
| 10 | **蓝牙 / Wi-Fi Direct** | 0 | 高（近距离） | 高 | 距离限制、需要配对，不适合"异网"场景 |
| 11 | **端口预测 / 生日攻击** | 0 | 低 | 高 | 现代 NAT 随机化端口后基本失效，不建议 |

## 三、推荐路线（按优先级）

1. **先把 IPv6 直连做扎实**（成本最低、收益最大）
   - 收集并优先使用 IPv6 srflx/host 候选
   - 在 P2P 页显示"当前网络：IPv4 NAT / IPv6 可用"
   - 如果双方都是 IPv6，成功率接近 100%，且完全绕过 NAT

2. **UPnP 双层探测**
   - 当前只映射了本机所在的一层；可以尝试对网关的网关再发一次 SSDP（需要跨网段，通常失败）
   - 实际价值有限，保持现状即可

3. **主机中转兜底**（阶段三的网页端）
   - 在 P2P 失败时，引导用户"用同一台设备开网页端，另一端用浏览器访问"
   - 这是零成本下唯一 100% 可行的跨网方案

4. **如果一定要"像微信一样"跨网**
   - 只有两条路：自建 TURN（需公网服务器）或接入 ZeroTier/Tailscale（需账号）
   - 两者都违背"零云成本 + 无账号"的原始红线，需要产品层面做取舍

## 四、不建议投入的方向

- 继续堆 STUN 服务器：对对称 NAT 无效
- 端口预测：现代 NAT 已随机化
- 纯 P2P 打洞覆盖所有网络：物理上不可能

## 五、给产品的建议

- 在 P2P 页明确显示当前网络类型与失败原因，不要让用户以为是 App 坏了
- 主打"同一 Wi-Fi 局域网直连"（稳定、零成本、速度快）
- 跨网场景默认引导到"网页端主机中转"，把 P2P 定位为"同网段/有 IPv6 时的加速通道"
